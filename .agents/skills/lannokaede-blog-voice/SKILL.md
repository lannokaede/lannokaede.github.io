# lannokaede 个人博客写作风格指南

写新文章或润色现有博客时，把这篇文章当成跟懂技术的朋友随口聊最近折腾的东西，而不是交实验报告、写架构白皮书或背简历。

## 1. 声音锚点（以作者亲自修订的 `self-hosted-aichat.md` 为准）

- **起手直接讲动机或槽点**：先说“之前怎么用着不顺手 / 为什么突然想折腾这事”，不要上来背项目头衔或罗列技术栈清单。
- **平时怎么说话就怎么写**：自然使用“干脆”“顺手”“搓了个”“嫌烦”“绕了点弯子”“挺省心的”“眼下先凑合”这类日常表达，句子长短交替，允许带一点随口的评价（例如“顺眼多了”“列表看看就行，不跑通别急着往菜单里塞”）。
- **像聊踩坑，不像写运维体检单**：不要连续三四段都是“版本锁在 X。模型走 Y。面板反代在 Z。”的机械汇报节奏，把配置背景顺着“当时怎么搭、后来哪里炸了、怎么修”的顺序带出来。
- **收尾自然停下**：聊完当下状态就行，没做完的直接说拖着还没做，**绝不写**“总而言之”“期待未来”“希望这篇对你有帮助”。

## 2. 重点规避的“AI 味”和“简历味”

1. **假对比 / 对偶壳**：少用“不是……而是……”“一是……二是……”“一方面……另一方面……”，除非真的是并列区分。
2. **播音腔 / 讲义过渡**：删掉“实际用的时候发现一个挺现实的问题：”“这里有个很容易忽略的地方：”“解决方式是……”“为了确认不会出岔子，还专门测过……”。
3. **简历式自我介绍**：提比赛奖项或项目背景时顺口带过即可，不要像答辩 PPT 那样一板一眼背架构和分工清单。
4. **公文动词与堆砌定语**：把“进行测试 / 开展排查 / 承担了……职责”改回直接动词。

## 3. 不可妥协的事实边界（同 `humanizer-zh`）

- **不编造任何未提供的事实**：不凭空加数据、版本号、时间线、踩坑剧情或情绪故事。
- **严格保留实测与未测状态**：测通的写测通，没来得及测或还没做的必须原样标清楚。
- **保护技术资产**：代码块、命令、路径、URL、版本号、YAML frontmatter 的 `slug`/日期/分类等保持准确，不因口语化而改歪专业术语。
