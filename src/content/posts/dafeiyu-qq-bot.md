给大肥鱼补视频识别的时候，我顺手把发给模型的原始消息翻出来看了一眼，这才发现群里发过去的视频，兜了一圈送到模型嘴边只剩 `[视频]` 两个字——有些路径明明拿到了文件地址，后面压根没往下抽帧。怪不得之前她点评群友发的视频总在胡言乱语，模型根本就没看见画面。

大肥鱼是我挂在 QQ 里的聊天机器人，人设照着社区的[大肥鱼人格文件](https://github.com/whyever77/dafeiyu-astrbot/blob/main/persona/大肥鱼-人格.md)改的，底座用 AstrBot 配 NapCat。趁着还没忘，把这段时间调群聊插话、表情包、长期记忆和视频抽帧踩的几个坑记一笔。

## 底座是怎么搭起来的

机器跑的是 OpenCloudOS 9.4，核心就两个容器：[AstrBot](https://github.com/AstrBotDevs/AstrBot)（锁在 `v4.29.1`）和 NapCat（锁在 `v4.18.41`），镜像顺手都钉死了 digest。NapCat 负责挂 QQ，走 OneBot 11 反向 WebSocket 把消息推给 AstrBot，过完插件和模型再把回复送回去。每次动配置或升级前，我都会把 Compose 文件、AstrBot 数据卷和 QQ 登录目录全备一份——登录目录最金贵，丢了就得重新扫码。

聊天模型懒得本地跑，直接接现成的 OpenAI 兼容网关，聊天和整理记忆都走 DeepSeek。这台服务器只干消息接入、跑插件，外加扛一个小向量模型。管理面板反代在 Nginx 后面走 HTTPS，后端端口只绑回环地址，平时在 `/opt/astrbot` 下看状态基本就这三条命令：

```bash
docker compose ps
docker compose logs --tail 100 astrbot
docker logs --tail 100 napcat
```

## 群里什么时候插话，怎么让它说人话

最开始用的是 AstrBot 自带的随机搭话，概率设成 15%。后来换成了 [Chat Plus](https://github.com/Him666233/astrbot_plugin_group_chat_plus)，把群聊要不要回全交给它判断（初始概率还是 0.15），自带的随机触发直接关掉。私聊照旧走原生流程；群聊交给 Chat Plus 之后，会带上最近 30 条消息、留 20 轮上下文，省得群里一刷屏她就接不上茬。

改大肥鱼人设的时候踩过个小坑：AstrBot 的默认人格和 Chat Plus 里的人格得两边同步改。只改默认人格的话，群里聊起来还是旧的那套设定。

说话习惯我砍改得挺狠。闲聊尽量压在一到三句里，不让她先复述一遍别人的话，也把原本每句必带“唔”“哼”的硬规则删了——偶尔卖个萌还行，写死之后聊两轮全是复读机味。社区人设里写的语音和生图我压根没接，就顺手把那些描述清掉了；群里称呼也按发言人分开，免得见谁都叫同一个外号。

## 表情包发不出去和网关报错

表情包用的是 `meme_manager`。先导了一小批图进去，每张图补好描述和向量，挑图时看最近几句对话和人设，一次最多发一张。自动收图只给指定群开了，加了采样率、冷却和去重，不然群里天天刷图，盘很快就被塞爆。

发图特意切成了 Base64。AstrBot 和 NapCat 分在两个容器里，AstrBot 认得的本地路径，传给 NapCat 那边经常读不到。

中间还碰上一次接口兼容报错：插件发请求时要求强制调 tool，网关不支持那个参数字段，直接甩回来一个错。后来在插件外围套了层兜底，撞上这个错就自动走插件自带的 JSON 回退逻辑，顺手补了条测试挡着——下次升级 `meme_manager` 得记得回头核对一眼，别一更新把补丁冲没了。

## 记忆塞进向量库被一刀截断

长期记忆装的是 [LivingMemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory)。聊天模型负责归纳记忆，检索靠本地 CPU 跑的 `BAAI/bge-small-zh-v1.5`（512 维，只监听回环地址）。

刚接好的时候测写入、召回和会话隔离都顺风顺水，结果真正跑了一阵、记忆长起来之后，本地向量接口突然报错拒收。一翻代码才看到两头上限没对齐：向量接口写死最多收 2000 字符，LivingMemory 聚出来的文本能飙到 4000 字符，前面拿短文本测试正好躲过去了。

把接口上限拉到 4000 字符后，长文本和批量请求总算不报错了。不过 `bge-small-zh-v1.5` 本身还是按 512 tokens 截断的，太长的记忆后半截其实没算进向量里，后面还得想想怎么在入库前拆短点。

## 视频抽帧撞上插件执行顺序冲突

视频识别用的是 [LLM 综合增强](https://github.com/Foolllll-J/astrbot_plugin_llm_enhancement)的媒体模块，自己在外面包了个精简入口。普通视频、引用消息里的视频、合并转发里的视频都会先捞出来扔给 FFmpeg 抽帧；纯文字消息直接跳过，群里插不插话照样听 Chat Plus 的。

刚挂上去就撞了个顺序坑：Chat Plus 发请求前会重写上下文，如果把视频抽帧结果塞在它前面，经过重写一洗，最后送到模型手里的请求经常把视频描述弄丢。后来把媒体解析挪到重写之后，保住人设和群聊上下文再把画面信息拼上去，这才稳了。

回复提示词我也调成了日常吐槽口吻。群友丢个梗视频进来，顺着画面里的动作或反差接一句就行，不用跟写阅读理解似的总结“这段视频的主题是……”。

验证时拿 FFmpeg 合成了段 8 秒测试短片（红球往蓝方块那边跑），直接发、引用和合并转发三条路都走通了真实模型，回复能准确说出画面里的东西和动作。目前看视频只靠抽帧和画面文字，还没接语音识别；超时也卡了上限，真读失败就老实说没看清，不让模型硬编画面。

## 扫码掉线，还有几项没测完

QQ 这边登录态挺脆的：有次手机明明扫完了，服务端也收到了事件，QQ 转头就返了个 `168`，提示账号有安全限制；还有一次存下来的登录凭据过期，快捷登录直接被拒，只能重扫。所以平时光盯 Docker 容器活着没用，还得看登录态。

10 月 28 日装完视频插件那轮检查，QQ 又卡在等扫码的状态。插件加载和服务端短片测试都已经过了，但还没真的往群里发过实测消息。等重新扫码登上去，还得在真实群聊里分别试一下普通视频、引用追问和带视频的合并转发，顺便看看群里压糊的视频和本地合成短片差多少。
