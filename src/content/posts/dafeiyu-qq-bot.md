给大肥鱼补视频识别时，我把传给模型的消息翻出来看了一眼，才发现群里发过去的视频，处理完送到模型嘴边只剩 `[视频]` 两个字。有些路径拿到了文件地址，后面压根没继续抽帧。怪不得以前她评价群友发的视频总是不着边际——模型压根没看到画面。

大肥鱼是我放在 QQ 里的聊天机器人，人设参考了社区的[大肥鱼人格文件](https://github.com/whyever77/dafeiyu-astrbot/blob/main/persona/大肥鱼-人格.md)，底座用 AstrBot 配 NapCat。这篇把折腾群聊插话、表情包、长期记忆和视频抽帧时踩到的几个坑顺手记一下。

## 怎么接进 QQ 的

服务器系统是 OpenCloudOS 9.4，主要跑两个容器：[AstrBot](https://github.com/AstrBotDevs/AstrBot) 和 NapCat。NapCat 负责挂 QQ，通过 OneBot 11 反向 WebSocket 把消息推给 AstrBot；AstrBot 过完插件和模型，再把回复送回去。

目前版本锁在 AstrBot v4.29.1 和 NapCat v4.18.41，镜像也固定了 digest。每次动配置或者升级前，都会把 Compose 文件、AstrBot 数据卷和 QQ 登录目录一起备份；尤其登录目录不能丢，丢了就得重新扫码。

聊天模型没有本地部署，直接接已有的 OpenAI 兼容网关，聊天和记忆整理都走 DeepSeek。这台机器上只跑消息接入、插件，以及后面要用到的一个小向量模型。

管理面板反代在 Nginx 后面走 HTTPS，后端端口只绑回环地址。平时在 `/opt/astrbot` 下看状态主要就这三条：

```bash
docker compose ps
docker compose logs --tail 100 astrbot
docker logs --tail 100 napcat
```

## 群里什么时候插话，怎么说话

一开始用的是 AstrBot 自带的随机搭话，概率设在 15%。后来装了 [Chat Plus](https://github.com/Him666233/astrbot_plugin_group_chat_plus)，把群聊要不要回的判断全交给它，初始概率还是 0.15，自带的随机触发关掉。

私聊还走 AstrBot 原生流程；群聊交给 Chat Plus 之后，会带上最近 30 条群消息，上下文留 20 轮，免得群里连续刷几句话时她接不上茬。

调大肥鱼人设的时候踩过一个小坑：AstrBot 的默认人格和 Chat Plus 里配的人格要两边一起改。光改默认人格，群聊那边照样还在用旧设定。

说话习惯我改得比较多。闲聊尽量压在一到三句里，不让她先复述一遍别人的问题，也把原本每句必带“唔”“哼”的规则删掉了——偶尔来一句还行，写死成规则之后，聊几轮全是一个味。另外社区人设里写到的语音和生图能力我没接，就顺手把对应的描述删了；群聊称呼按发言人区分，不把谁都叫成同一个外号。

## 表情包和模型兼容问题

表情包用的是 `meme_manager`。先导了一小套图库进去，给每张图补好描述和向量，挑图时会参考最近几句对话和当前人设，一次最多发一张。自动收图只在指定群开启，加了采样率、冷却和去重，不然群里每天发的图全存下来很快就把盘塞满了。

发图特意切成了 Base64。因为 AstrBot 和 NapCat 分别在两个容器里，AstrBot 看到的本地路径，传给 NapCat 那边不一定读得到。

中间还撞上过一次接口兼容报错：插件发请求时要求强制调用 tool，但网关不支持对应的参数字段，直接返回报错。后来在插件外围补了一层兜底，触发这个错就走插件自带的 JSON 回退逻辑，另外写了条测试挡着——下次升级 `meme_manager` 得记得重新核对这处改动，免得更新一覆盖又坏了。

## 记忆塞进向量库时被截断

长期记忆装的是 [LivingMemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory)。聊天模型负责归纳记忆，检索靠本地 CPU 跑的 `BAAI/bge-small-zh-v1.5`，输出 512 维向量，服务只监听回环地址。

刚接好的时候测了写入、召回和会话隔离，一切正常。等真正跑起来、积累了长一点的记忆记录，本地向量接口直接报错拒收。

一查才发现两边的长度上限没对齐：向量接口写死最多收 2000 字符，而 LivingMemory 聚出来的文本能到 4000 字符，早期的短文本测试刚好绕过了这条线。

把接口接收上限放到 4000 字符后，长文本和批量请求不再报错了。不过 `bge-small-zh-v1.5` 本身还是按 512 tokens 截断，太长的记录后半段其实没参与算向量，后面还得考虑在入库前把长记忆拆短。

## 接上视频抽帧时遇到插件顺序冲突

视频识别用的是 [LLM 综合增强](https://github.com/Foolllll-J/astrbot_plugin_llm_enhancement)的媒体模块，自己另外包了一个精简入口。普通视频、引用消息里的视频、合并转发里的视频都会先从这里提取出来，丢给 FFmpeg 抽帧。普通纯文字消息直接跳过，要不要在群里插话还是 Chat Plus 说了算。

接上去之后发现一个执行顺序问题：Chat Plus 在发请求前会重写上下文。如果把视频抽帧结果插在它前面，经过重写之后，最后送到模型手里的请求往往把视频描述弄丢了。所以得把媒体解析放到重写之后，保住原有的人设和群聊上下文，再把视频信息拼上去。

回复提示词也顺手改成了日常吐槽的口吻。群友丢一个梗视频进来，她能顺着画面里的动作或反差接一句就够了，不需要正经八百地总结“这段视频的主题是……”。

验证时拿 FFmpeg 合成了一段 8 秒测试短片（红球向蓝方块靠近），直接发、引用和合并转发三条路都走通了真实模型，回复能准确提到画面里的物体和动作。现在看视频主要靠抽帧和画面文字，还没接语音识别；超时也卡了上限，真读失败了就明说失败，要求模型别瞎编画面。

## 扫码掉线和还没测完的地方

QQ 这边登录态挺脆弱：有一次手机上明明扫完了码，服务端也收到了事件，QQ 紧接着返了个错误码 `168`，提示账号存在安全限制；另一次是保存的登录凭据失效，快捷登录直接被拒，只能重新扫码。所以光看 Docker 容器是不是活着没用，还得盯登录状态。

10 月 28 日装完视频插件那轮检查里，QQ 又停在等待扫码状态。插件加载和服务端短片测试都已经过了，但还没真的往群里发过实测消息。等重新扫码登录后，还得在真实群聊里分别试一下普通视频、引用追问和带视频的合并转发，顺便看看群里被压糊的视频和本地合成短片有多大差别。
