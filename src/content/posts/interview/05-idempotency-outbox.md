> **复习标记：重点不会** · 本文按真实模拟对话整理。“当时回答”与“我的追问”为原话摘录或明确标注的归纳；参考答案是整理后的解释，不表示已独立掌握。

把重复请求、换 ID 重复业务、同 ID 参数冲突和跨系统通知分开处理。

## Q1：同一 requestId 再次提交，是冲突吗？

**当时回答经历了两次混淆**：同 ID 不同活动认为可以继续领；同 ID 同参数又认为是冲突。

### A：先固定幂等作用域，再比较参数

| 情况 | 处理 |
| --- | --- |
| 相同 ID、相同参数，已有成功回执 | 返回原结果，不重复执行 |
| 相同 ID、不同参数 | 返回幂等键冲突 |
| 不同 ID、同一用户领取同一活动 | 依靠业务约束防止多领 |

项目作用域还包含商家、操作者和操作类型。ID 标识“哪次操作”，参数摘要检查“内容有没有变”。

**我的追问式理解**：“报冲突用户就不知道自己成功领到券了。”

这个理解有道理：正常重试应确认原结果，而不是把重复 ID 一律视为错误。

---

## Q2：换一个 requestId，就能再领一张吗？

**当时回答**：“对用户 id 进行验证，每个用户只能领一次。”随后提出用用户 ID 作主键。

### A：约束同一活动与同一用户的组合

概念示例：`UNIQUE (campaign_id, customer_id)`。仅用用户 ID 作主键，会阻止同一用户参加另一个活动。真实表字段与商家作用域以项目实现为准。

先查询“领过没有”不够，两个并发请求可能同时查到没有，需要数据库唯一约束等机制兜底。

---

## Q3：券和成功回执为什么一起提交？

**当时回答**：“领了券没有回执，导致重复领取。”

### A：防止业务成功、回执缺失的部分状态

但项目还有业务唯一约束，所以不能说一定能插入第二张券。回执缺失会让重试无法直接确认原结果，需要处理已有业务记录或约束冲突。

---

## Q4：外部短信能跟数据库事务一起回滚吗？

**状态：第一轮结束时提出，但没有作答。** 后续在缓存失效补偿中讲解了 Outbox。

### A：本地事务不能撤回外部已经发生的动作

数据库回滚不等于已发出的短信可以收回。可以先在同一数据库事务里保存业务与 Outbox 事件，再由后台派发；外部发送后确认丢失仍可能重复，需要幂等、重试与对账。

项目当前通知是同 PostgreSQL 事务中的模拟通知，不是已接入真实短信平台。

---

## Q5：缓存删除失败，Outbox 怎样补救？

```text
数据库事务：更新价格 + 保存缓存失效事件
后台：读取事件 → 删除 Redis key → 标记完成
```

失败可以重试，避免仅在进程内安排一次重试，重启就丢掉。TTL 作为兜底，但这仍不保证数据库和缓存任何时刻都严格一致。

**复测**：分别解释“防重试”“防业务重复”“防超发”“保证本地一起提交”由哪些机制承担。
