把另一套 Agent 系统当作任务服务，认识名片、消息、任务和交付产物。

## Q1：已有 MCP，为什么还需要 A2A？

**当时回答**：不太了解，要求详细讲解。

### A：它们描述不同的交互

MCP 统一访问工具与资源；A2A 规范独立 Agent 系统之间如何委托任务、交换消息、查询进度与获取结果。

```text
外部平台 --A2A--> 商家经营 Agent
                        └→ 内部模型与工具编排
```

外部平台委托“完成经营分析并给方案”，不需要知道内部每次查询和工具选择。工具也可能复杂、长耗时，因此不能只用耗时区分两种协议。

---

## Q2：Agent Card、Message、Task、Artifact 是什么？

| 对象 | 直观理解 |
| --- | --- |
| Agent Card | 能力、入口、交互与鉴权要求的名片 |
| Message | 需求、补充信息、说明等交互消息 |
| Task | 有 ID、状态和生命周期的工作单元 |
| Artifact | 文档、报告、结构化结果等交付产物 |

具体字段和可用操作以协议及 SDK 版本为准，不要求每次请求都变成长任务。

---

## Q3：一轮任务怎样继续澄清？

```text
提交目标 → 返回任务 ID → 查询执行状态
→ 需要补充条件 → 提交补充消息 → 继续处理 → 返回结果
```

协议支持多种交互能力，但是否支持流式、推送、文件等，需要查看服务端实际声明与实现。

---

## Q4：当前项目哪些是已实现，哪些不是？

通过官方 Go SDK 接收 A2A 请求，复用 PG 队列；要求异步受理后轮询查询，支持取消、澄清续接和归属校验。内部创建子运行，对外保持根任务 ID。

内部分析、方案双 Agent 仍是同进程顺序协作，**不是通过 A2A 相互调用**。人工发布在经营页面完成，不能通过协议绕过审批。

**复测**：一句话分别说明 Function Calling、MCP、A2A，并举同一个项目中的位置。
