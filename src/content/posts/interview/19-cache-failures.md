> **复习标记：重点不会** · 本文按真实模拟对话整理。“当时回答”与“我的追问”为原话摘录或明确标注的归纳；参考答案是整理后的解释，不表示已独立掌握。

用“数据不存在、一个热门 key、大批 key”区分三个常见名词。

## Q1：不停查询不存在的商品 ID，叫什么？

**当时回答**：不清楚。

### A：缓存穿透

缓存与数据库都没有，每次都访问数据库。可以缓存短 TTL 的“不存在”标记、校验参数、限流；大规模场景可考虑布隆过滤器，但要维护数据同步并接受可能误判“存在”。

空结果缓存适合挡住同 ID 重复查询；不断换新 ID 时效果有限。空结果与“尚未缓存”需要能区分。

---

## Q2：一个热门商品缓存刚过期，大量请求回源？

**当时回答**：认为是缓存雪崩，并建议热点不过期或定期更新。

### A：通常叫缓存击穿

单个热门 key 失效。可以合并回源请求，单进程用 singleflight，多实例可考虑共享协调；允许旧数据时保留旧值并后台刷新。

永不过期也要处理更新、旧值和刷新失败，不是简单取消 TTL 就结束。

---

## Q3：大量 key 过期时间相同呢？

**当时回答正确**：缓存雪崩，设置不同失效时间；还提出限制同时失效个数。

### A：分散过期并控制回源压力

例如 30 分钟基础 TTL 加 0～5 分钟随机偏移，避免集中到期。通常不直接限制“几个 key 能过期”，更实用的是限制回源数据库的并发、做降级与容量保护。

Redis 整体故障也可能形成大面积回源，不能只靠 TTL 随机化处理。

| 名称 | 典型起因 |
| --- | --- |
| 穿透 | 查不存在的数据 |
| 击穿 | 单个热门 key 失效 |
| 雪崩 | 大量缓存同时失效或缓存服务故障 |

**复测**：不背名字，先描述为什么数据库流量增加，再选处理方法。
