> **复习标记：重点不会** · 本文按真实模拟对话整理。“当时回答”与“我的追问”为原话摘录或明确标注的归纳；参考答案是整理后的解释，不表示已独立掌握。

频繁 GET 不会自动续期，过期时间与内存压力下的淘汰是两套机制。

## Q1：限流 key 为什么设置过期时间？

**当时回答正确**：不设置就占内存不释放。

### A：清理不再需要的旧窗口

每分钟生成新 key，旧 key 如果不显式删除、过期或被淘汰，可能持续占用内存。TTL 表达数据有效期，不能与回收触发时刻混为一谈。

---

## Q2：达到内存上限一定按 LRU 清理吗？

**当时回答**：会按 LRU 删除最久未使用的。

### A：看配置的淘汰策略

LRU 偏向淘汰最近最久未访问的键；LFU 偏向淘汰低频访问的键；`noeviction` 不主动淘汰，无法容纳相关新增或扩容写入时会报错。还有其他策略，以及针对所有键或仅带 TTL 键的区别。

Redis 使用近似实现，不必现在背完整策略清单，但不能说一定自动清理。

---

## Q3：60 秒到期，一定瞬间释放内存吗？频繁 GET 会续期吗？

**当时回答**：频繁访问会推迟过期，LRU/LFU 清理。

### A：普通 GET 不改变 TTL

过期键通过访问时检查的惰性删除，以及后台周期性抽样清理等机制回收。逻辑上已过期时，正常读取不应继续返回旧值；物理内存释放不必恰好发生在到期瞬间。

LRU/LFU 是内存压力下的淘汰，不是过期清理。访问频繁影响淘汰选择，不会自动延长 TTL；需要显式续期操作。

---

## Q4：普通 SET 更新已有 String，保留 TTL 吗？

**当时回答**：不会，但认为更新时间。

### A：普通 SET 会清除原 TTL

```text
SET product:1 old EX 60
SET product:1 new
TTL product:1
```

最后返回 `-1`，表示存在但不过期。重新设置 60 秒使用 `SET ... EX 60`；保留原过期时间可用 `KEEPTTL`。不能把这个结论推广到所有修改命令。

---

## Q5：限流记录没到期就被淘汰，有什么后果？

**当时回答正确**：限流不严格，用户可能突破限制。

删除后重新计数，相当于额外获得额度。本地限流不能恢复跨实例共享历史。

**复测**：不看表，分别解释“逻辑到期、物理清理、内存淘汰、显式续期”。
