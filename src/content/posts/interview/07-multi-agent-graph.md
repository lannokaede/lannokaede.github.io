> **复习标记：易混淆** · 本文按真实模拟对话整理。“当时回答”与“我的追问”为原话摘录或明确标注的归纳；参考答案是整理后的解释，不表示已独立掌握。

拆分不自动更快，使用框架也不自动获得恢复、幂等和业务正确性。

## Q1：为什么拆分析 Agent 和方案 Agent？

**当时回答**：多 Agent 效率高、减少长上下文消耗、明确权限边界。

### A：权限与职责可以更清楚，性能收益需要测量

分析 Agent 只读，方案 Agent 根据分析与用户目标生成方案。拆分可能减少单个角色看到的无关信息，但串行执行和信息交接也增加模型调用及 token 成本，不能直接说更快、更省。

---

## Q2：两个 Agent 之间传什么？

**当时回答**：客源分析结果；预算在数据库，用户目标从输入获取，“吧”。

### A：要能明确说明信息的用途

用户目标、分析结论是推理上下文；预算还需要在工具执行时由可信业务状态强制校验。当前是同进程顺序角色协作，不等于通过 A2A 远程通信。

该题暴露了对实际传递方式不确定，后续应对照源码画数据流，不靠猜测补全。

---

## Q3：为什么用 LangGraphGo，不手写循环？

**当时回答**：不太清楚，并提到“现在 Agent 开发很少用框架”。

### A：按实际收益说明取舍，不用行业口号代替理由

项目运行器把模型和工具做成节点：

```text
模型节点 → 有工具调用 → 工具节点 → 模型节点
        → 最终答案 → 结束
```

LangGraphGo 负责节点与条件路由。当前两个节点用普通循环也能实现，框架收益有限；后续分支复杂时，显式状态图可能更便于组织。

模型接入、参数校验、业务事务、持久任务、取消和幂等仍由自己的代码实现。项目没有使用图检查点续跑，不应套用 Python LangGraph 的全部能力。

---

## Q4：同一轮多个工具能全部并发吗？

**当时回答**：有依赖要串行，同级工具可并发，保存草案放最后。

### A：按数据依赖、冲突和副作用判断

独立只读查询可以考虑并发；有依赖或写入冲突应串行。但“保存一定最后”不是通用规则，当前项目实际是工具串行执行，并没有自动依赖调度。

**追问**：先执行查询，再执行同轮保存，就用上新结果了吗？

不能保证。保存参数在模型生成这一轮调用时已经确定。先把查询结果返回模型，让模型据此生成后续调用，才形成新的决策依据。

**复测**：解释哪些能力来自框架，哪些来自业务代码，并画一轮模型与工具交互。
