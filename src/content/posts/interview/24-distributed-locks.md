跨进程协调、原子抢锁、安全释放，以及锁过期却没有停止旧执行者的问题。

## Q1：三个实例各加一个 sync.Mutex 够吗？

**当时反问**：“不同实例能加同步锁吗？每个后端单独加也锁不上啊。”

### A：本地锁互不可见，需共享协调

多个实例竞争同一个 Redis key，拿到的实例重建对应商品缓存。锁不是暂停所有进程的按钮，所有参与者都要遵守获取资格的规则。

```text
SET lock:product:123 token-A NX PX 5000
```

`NX` 不存在才设置；`PX` 同时设置租期；token 标识本次获取。不要拆成创建锁、再设置 TTL，两步之间崩溃可能留无期限锁。

## Q2：为什么释放不能直接 DEL？

```text
A 拿锁 → 执行过久 → 锁过期
B 拿到同 key 的新锁
A 执行结束，直接 DEL → 误删 B 的锁
```

### A：核对 token 后原子删除

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

比较和删除不能在应用中拆成两个普通命令。这里使用兼容较多版本的 Lua 形式，实际也可按版本选择原子条件删除能力。

---

## Q3：分布式锁只是准入口？失效不会停止进程？

**我的核心追问**：“不是严格意义的锁，只是准入口；失效不代表停止当前进程？”

### A：可以理解为带期限的执行许可，但它仍是一种锁

过期后旧代码不自动停止，可能和新持有者并行。续期可以降低风险，但进程暂停、网络异常仍可能导致租期失效。

随机 token 防误删，不会阻止旧执行者继续写。更严格场景可让存储校验版本或可靠递增 fencing token，拒绝过期写入；不能把随机标识与 fencing token 当同一东西。

---

## Q4：缓存重建完整流程是什么？

```text
查缓存 → 未命中 → 抢资源对应的锁
  成功：再次查缓存 → 仍无则查库回填 → 安全释放
  失败：有限等待后重查，或按业务降级
```

锁后再次检查，避免等待期间别人已经重建。等待必须有边界，TTL 也不能承诺严格互斥永不失效。

---

## Q5：能替代数据库发券事务吗？

不能只靠它替代本项目的行锁、唯一约束和幂等。Redis 主从异步复制和故障切换还可能丢锁。当前项目 Redis 主要限流，分布式锁是本轮学习的可选设计，不是项目成果。

**复测**：说明 `NX`、TTL、随机 token、安全释放分别防什么，哪些问题它们仍防不住。
