## Q1：△ Redis 就是所有查询必经的缓存层吗？

不是。只有设计了缓存的查询才先查 Redis；它还可做共享计数、限流等。进程内 map 不跨实例共享，Redis 可供多个实例共同访问，但增加网络与服务故障成本。

**我的疑问**：“查询都走 Redis、写入直接进数据库？”这是部分旁路缓存用法，不是通用规则。写数据库后还要处理已有缓存失效。

缓存优先放高频、查询成本高的数据。Redis 支持持久化，不能用“不能落盘”解释为何不缓存全量；主要权衡内存成本与一致性维护。

---

## Q2：★ 缓存怎样读写，异常怎样区分？

旁路缓存：读时未命中就查库回填；写时先更新数据库，再删缓存。删除失败需有限重试或可靠补偿，TTL 兜底。

| 异常 | 典型情况 | 基本应对 |
| --- | --- | --- |
| 穿透 | 反复查不存在的数据 | 空结果缓存、参数校验、限流 |
| 击穿 | 一个热门 key 失效 | 合并回源、受控后台刷新 |
| 雪崩 | 大量 key 同时失效或 Redis 故障 | 分散 TTL、限制回源、降级 |

**我的反问**：“不是还有其他缓存方式？”有：Read Through 把加载封装在缓存层；Write Through 同步更新；Write Behind 异步落库。它们都不是 Redis 自动开启的功能，也不自动保证跨系统原子性。

## Q3：★ 单线程为什么还需要 Lua？会自动回滚吗？

普通命令主要串行执行，但“查数量→判断→增加”是多个命令，可能被其他请求穿插。Lua 把检查与修改组合执行，避免双方都根据旧值决策。

**最重要的区别：原子执行不等于自动回滚。** 脚本后面报错，前面成功写入不会自动撤销；防重试也需要显式去重逻辑。

Redis 不是整个进程只有一个线程，网络 I/O 和后台任务可由其他线程或进程承担。长 Lua、慢命令仍可能拖慢其他请求。

---

## Q4：★ TTL、LRU/LFU 是不是同一种清理？

不是。TTL 是到期失效，通过访问检查和周期性清理等方式回收；LRU/LFU 是达到内存上限时的淘汰策略，还可能配置为不淘汰、相关写入报错。

**当时误区**：认为频繁 GET 自动续期。普通 GET 不改变 TTL；普通 `SET key value` 则会清除旧 TTL，重新设期限用 EX/PX，保留原期限用 KEEPTTL。

逻辑到期不表示恰好那一瞬间释放内存。限流 key 提前被淘汰，会丢计数、额外放行。

## Q5：△ 限流、worker、滑动窗口分别管什么？

限流管时间内请求量，worker 管同时执行任务数。固定自然分钟窗口可能在边界瞬间放行两倍额度；滑动窗口日志可用 Sorted Set 按时间清旧记录、计数、登记，并用 Lua 组合执行。

项目用 Hash 登记每用户每分钟的请求 ID，相同 ID 不重复占额度。Redis 故障退化为本地限流，多个实例各自记账，无法继续保证全局额度。

限流是资源保护，不是库存和预算的一致性证明。

## Q6：★ RDB、AOF、复制、Cluster 有什么区别？

| 机制 | 一句话理解 |
| --- | --- |
| RDB | 保存某一时刻的数据快照 |
| AOF | 记录用于恢复的写操作，持久性取决于同步策略 |
| 主从复制 | 其他实例保存副本；默认异步，可能延迟或丢部分故障前写入 |
| Sentinel | 监控并协调自动故障切换 |
| Cluster | 不同 key 按槽分给不同主节点，承担容量和负载 |

**当时能答出**：增加从节点只是增加副本，不是分片扩容。Cluster 记住“key→16384 个槽之一→节点”即可；原生多 key 操作通常要求同槽。

---

## Q7：★ 分布式锁为什么只是有期限的执行资格？

跨实例不能靠各自的 Mutex。Redis 可用 `SET lock token NX PX ...` 原子抢锁并设期限，释放时原子核对 token 再删除，防止旧持有者误删新锁。

**我的关键反问**：“锁失效不代表停止当前进程？”对。旧代码可能继续执行，续期也不能消灭所有故障；关键写入仍需数据库约束、版本等保护，不能只靠租期锁。

当前项目未把 Redis 分布式锁作为已实现能力，仍以数据库保障发券一致性。

---

## Q8：△ 批量访问与两级缓存怎样减少开销？

批量读 String 可用 MGET；多命令可用 Pipeline 减少网络往返，但不自动保证整体原子。

**我的反问**：“100 个 GET 写进 Lua 行吗？”可以，但单纯批量读取通常 MGET 更简单；脚本仍串行执行，不宜过长。

本地缓存比访问 Redis 少一次网络，但每实例各有一份，更新失效更复杂。大 key 是值大或元素多，热 key 是访问集中；排障先分清客户端、网络、Redis 执行和数据库回源哪段慢。

---

## Q9：★ 超时、消息、缓存命中能不能当成功证明？

- **INCR 响应超时**：可能已执行，直接重试可能多加一次；原子命令不等于业务幂等。
- **Pub/Sub 发布**：断线不补收，在线收到也不等于处理完成；关键通知需要可靠记录与重试。
- **缓存命中**：仍需身份隔离与有效期，key 要包含商家等影响结果的因素。
- **模型回答缓存**：输出随机不是不能缓存的原因，是否可安全复用才是关键；缓存文本不能代替写工具执行。
