《织课》是我们团队拿了第十七届服务外包创新创业大赛全国二等奖的项目，后来也实际拿去给《人工智能时代》这门课备课用，覆盖了近千名学生。我在里面负责全部业务后端的设计、开发和部署，还有跟前端、Python AI 服务之间的联调。

业务后端用的是 Go、Gin 和 GORM，结构化数据放 PostgreSQL，素材和生成的课件文件丢进 MinIO，异步任务走 RabbitMQ，缓存和限流用 Redis；Python 那边跑的是团队集成的 LangGraph、LightRAG 和 pgvector。

## 为什么不能同步等课件生成

生成一套课件要经过文档解析、视频转写、检索和大纲拼装，动辄几十秒到几分钟，HTTP 请求根本不可能一直挂着等。

所以接口入口先用 Redis Lua 按用户做了一层原子限流，参数校验完就把任务塞进 RabbitMQ，马上把任务状态和编号还给前端。

消费端这边不敢放开并发跑，靠预取数和固定大小的 worker 池压住在途任务，配合手动 ACK、消费幂等和有限次重试来兜住消息重复投递或中途失败。往下调 Python 服务时也加了信号量和超时取消，不然几个大文件同时冲进来，推理服务直接就拖垮了。

## 用 singleflight 挡住同一份课件的重复预览

课件元数据带版本号缓存在 Redis 里。实际用的时候发现一个挺现实的问题：备课或者课堂上，好几个人同时点开同一个版本的课件做预览导入，就会瞬间打出好几路一模一样的请求去拉 MinIO 和做格式转换。

我在 Go 服务里加了一层 `singleflight`，按课件版本号把并发进来的导入请求合并成一次：第一个请求去回源拉文件、转格式，后面撞上来的请求直接等同一份结果。单实例进程内的并发热点靠它就能挡住大部分重复开销；后面如果扩成多实例部署，跨进程的重复还是得靠共享存储和数据库里的版本状态锁来兜底。

## 阶段联调和 OnlyOffice 的版本回调

业务上把素材上传、需求澄清、大纲审核和产物下载拆成了几个清晰的阶段接口，两边主要把字段和状态流转对齐，省得前面大纲还没确认后面就开始生成。

在线编辑接的是 OnlyOffice。这里有个很容易忽略的地方：给 OnlyOffice 传的文档 `key` 必须把版本号带上。如果不同版本还用同一个 `key`，OnlyOffice 会直接拿缓存里的旧文件顶上来，根本不会去重新拉取更新。

用户在网页里改完点保存后，OnlyOffice 会回调 Go 后端。后端再去把改好的文件拉回来写进 MinIO，同时在库里新加一条版本记录，旧版本照样留着，这样历史回退和在线预览都能对上号。
