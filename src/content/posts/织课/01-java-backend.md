织课里，用户的一次操作往往会经过多个服务。上传资料以后要形成需求，调用团队的 PPT 生成服务，拿到产物，再进入预览与编辑。只看 Controller 很容易觉得流程不长，真正联调时，却要反复确认每一步成功代表什么。

回头整理 Java 学习路线，我会先沿着一份课件追踪数据，再回来看框架功能。

## 先画对象关系，再分层

用户、课件、文件和版本之间是什么关系？生成结果对应哪份需求？在线修改后，当前版本指向哪里？这些问题先确定，Controller、Service 和 Mapper 才有比较自然的边界。

Controller 接收参数和返回结果，Service 协调业务操作，Mapper 处理数据访问。分层的价值是让一个变化有明确落点：例如存储地址变了，不必让每个接口都重新拼路径；版本检查变了，也不该散落在多个 Controller。

学习时可以先完成普通 CRUD，再加入校验、统一错误和事务。每次都沿着实际调用链看它解决了什么，避免只记注解名称。

## 文件内容与文件记录分开理解

MySQL 保存的是课件与文件元数据、归属和版本等记录，文件二进制由 MinIO 保存。数据库里存在一条记录，不代表对象存储里的内容一定可读；对象上传完成，也不代表数据库已经切换到新版本。

我会用这几个问题检查设计：文件是谁的？用户现在打开哪个版本？历史版本是否还能找到？下载地址过期后，是否能从稳定的对象标识重新生成？

这些问题也帮助我理解 DTO 与持久化对象的差别。返回给页面的数据应当服务于当前操作，没必要把数据库字段原样全部暴露出去。

## 把远程调用的时间算进去

PPT 生成和文件下载都可能很慢。复盘时，我会先检查超时、错误传递和状态表达，再考虑异步化。前端需要知道是在等待生成、等待下载，还是已经有文件可编辑。

数据库事务尤其需要控制范围。远程服务耗时与数据库写入不是同一种操作，长时间等待外部调用会占住连接和锁。后续设计可以先保存待处理状态，远程步骤完成后再用短事务确认；若引入后台队列，还要继续补恢复和重复执行语义。

这里写的是我重新设计时的检查顺序，不能据此把完整持久任务系统算作织课已完成的能力。

## 并发预览让我重新理解 Future

已有实践中，用 `ConcurrentHashMap` 与 `CompletableFuture` 合并单实例内同一课件的并发预览导入：让多个等待方共享一次下载和写入结果。

理解它时，我会追踪四个时刻：谁成为首个执行者，其他请求等待哪个 Future，失败如何传给等待方，以及完成后何时清理映射。还需要检查旧任务清理会不会误删同一键的新任务。

这个方法的作用范围是同一 JVM。多个服务实例各有一份 map，仍可能重复执行；它也不能代替文件版本和数据库约束。

这段经历让我更愿意从业务对象学习 Java。集合、Future、事务和依赖注入，最后都落在一个具体问题上：多个请求同时处理同一份课件时，后端怎样给出稳定、可理解的结果。
