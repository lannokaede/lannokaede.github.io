租了一台美国 VPS，总得给它找点事情做。除了部署服务，一个很直接的用途，就是搭一套自己管理的代理。

刚开始，这件事看起来很简单：服务端装好，客户端导入节点，网页能打开，似乎就可以收工了。但往后多走几步，问题才慢慢冒出来：自己的订阅和朋友的订阅要不要分开？流量怎么算？每个月怎么重置？出口 IP 已经是美国，为什么检测页面里还会出现国内 DNS？

这篇就把这次搭建中值得留下的东西串起来。环境和配置以这台 VPS 为准，地址、订阅令牌和密钥均省略，不是一份可以原样粘贴的配置文件。

## 先认清这台小服务器

这台机器运行的是 **Ubuntu 22.04.5 LTS**，x86_64 架构，2 核、约 2 GB 内存。配置不算宽裕，还承担着其他服务，所以我更关心的是让这套代理方便管理、出了问题容易查。

确认系统其实只需要一条命令：

```bash
cat /etc/os-release
```

把实际环境记清楚很有必要。过一段时间再回头看教程，最容易忘记的恰好就是这些“当时觉得肯定记得住”的细节。

最终跑起来的组合是 **3x-ui + Xray**，代理协议用 **VLESS / TCP / REALITY / Vision**，电脑端用 Clash Verge，底层是 Mihomo。

平时说起来是一整套方案，但各部分做的事情并不一样：3x-ui 负责用户、订阅和流量管理，真正转发代理流量的是 Xray；REALITY 是传输安全配置，Vision 对应这里使用的 `xtls-rprx-vision` flow。[3x-ui 项目说明](https://github.com/MHSanaei/3x-ui)和 [Xray 传输配置文档](https://xtls.github.io/config/transport.html)可以作为进一步查阅的入口。

## 把“连接代理”和“领取配置”分开看

这套服务有两条容易混在一起的路径。

平时访问网站时，流量经过本机客户端，再进入 VPS 上的 Xray。这台机器的代理入口使用 TCP 443。

更新订阅时，客户端访问的是另一条 HTTPS 地址，拿回节点和规则配置。这里由 Nginx 提供 HTTPS 入口，使用 TCP 8443。它负责配置分发，不是日常代理流量的入口。

```text
访问网站：电脑上的 Clash Verge → VPS:443 → Xray → 目标网站
更新订阅：电脑上的 Clash Verge → VPS:8443 → HTTPS 订阅入口
管理服务：本机 SSH → 仅监听回环地址的 3x-ui 面板
```

这样理解之后，“订阅更新成功，但节点连不上”就不奇怪了。它只说明配置领取那条路通了，代理握手、分流规则和目标网站访问仍然需要分别确认。

管理面板则只监听 `127.0.0.1`，没有直接放到公网。需要操作时，可以借助 SSH 隧道：

```bash
# VPS_HOST 替换成自己的服务器地址
ssh -N -L 15432:127.0.0.1:54321 root@VPS_HOST
```

隧道建立后，再通过本地转发端口访问面板的实际管理路径。这比为了偶尔改一次配置，长期向公网开放管理入口更符合我的使用习惯。

## 一个节点，几份各自独立的订阅

自己用和分给朋友用，需求其实不一样。

我给自己的身份设置了软件层面不限额，另外建了三个独立身份，每个每月 **200 GiB**。这样某一个人的额度用完，只停用对应身份，不会牵连其他人。

这里真正起作用的是独立的客户端身份。把同一条订阅链接复制三份，并不会自动变成三份独立额度。反过来，同一个身份导入多台设备，流量也会合并计算。

配额的口径也需要提前说清楚。这次配置的 200 GiB 是：

```text
200 × 1024 × 1024 × 1024 = 214748364800 字节
```

统计的是实际经过代理服务的上传与下载之和。规则模式下，直接访问、不经过这台 VPS 的流量，不会计入这份代理配额。

当然，自己的身份设置“不限额”，只是这套软件不限制它。服务器厂商的套餐流量、端口速率和线路状况依然是另一层约束。

为了方便理解账期，这次还补了按日历月续期的维护逻辑：**北京时间每月 1 日零点**清零普通身份的用量，恢复因额度耗尽而停用的身份。这里是本次部署额外实现的行为，不能把它理解成安装面板之后天然就有的默认设置。

服务端验收里检查了计量、额度耗尽停用、重置恢复和身份之间互不影响。比起只看面板上填了多少数字，我更在意这些边界情况是不是真的按预期工作。

## 最值得记下的坑，出现在 DNS 上

这次最有意思的部分，是“已经能用了”之后才发现的问题。

检测页面里，网页出口和 WebRTC 显示的出口都是美国服务器，但 DNS 检测同时出现了国内解析器。也就是说，只看出口 IP，还不足以判断整条访问路径是否符合预期。

往下检查，发现有两层配置需要处理。

第一层是订阅。初版订阅没有下发完整的 DNS 策略，后续需要补齐。

第二层是客户端。订阅内容更新之后，Clash Verge 自身的 TUN 设置仍然覆盖了订阅中的部分内容。当时实际生效的严格路由选项还是：

```yaml
tun:
  strict-route: false
```

这也是这次最值得记住的一点：**订阅里写了什么，和客户端最终用了什么，中间还隔着一层合并与覆写。**

排查到最后，需要在客户端的 TUN 设置里开启严格路由，并检查 DNS 覆写是否覆盖了订阅策略。Mihomo 文档专门说明了 Windows 下 `strict-route` 与多宿主 DNS 泄漏的关系；具体行为和限制可以看 [TUN 配置说明](https://wiki.metacubex.one/config/inbound/tun/)。

不过，开了一个选项也不等于从此可以跳过检测。这次记录能确认的是问题定位和需要调整的设置，不能把它写成所有设备都已经完成了最终验收。浏览器自己的加密 DNS、IPv6、多网卡和客户端覆写，都可能影响实际路径；规则模式本来就允许部分流量直连，也要结合预期策略判断结果。

后面再检查类似问题，我会先看客户端最终生效的配置，再看连接记录和检测结果，而不是只盯着订阅文件里那几行 YAML。[Mihomo DNS 文档](https://wiki.metacubex.one/config/dns/)里对不同解析器字段的区分，也比一份来路不明的“万能 DNS 配置”更有帮助。

## 让它下个月还能正常用

代理服务本身之外，这次也把证书和备份一起安排了。

订阅的 HTTPS 入口使用 Let's Encrypt 的 IP 地址证书，部署了每六小时检查一次的续期任务。这里的证书服务于 HTTPS 订阅入口，和 REALITY 代理连接是两件事，不应该混在一起理解。

证书续期不能只看定时器有没有启用。已有验收记录里执行过续期模拟，并检查了 Nginx 配置与重载钩子。毕竟证书更新到磁盘之后，服务也得真正加载它。

备份则安排在服务器本地时间每天 03:15，保留最近七个日期，采用 SQLite 一致性备份，避免把运行中的数据库随手复制一份就当作完成了。这次也做过备份恢复验证。

平时想快速看看服务是否还在，可以先从这些命令开始：

```bash
systemctl is-active x-ui nginx
systemctl list-timers --all
journalctl -u x-ui -n 50 --no-pager
```

日志适合自己排查，公开分享前则要先检查里面有没有真实地址、用户标识和订阅信息。订阅链接本身就含有连接凭据，没必要为了转换格式，把它交给陌生的在线转换站。

## 折腾完之后

回头看，这次花心思的地方，已经不只是把一个节点搭起来。

独立身份解决的是几个人怎么各用各的；配额和日历月重置解决的是长期管理；证书和备份解决的是以后少一点临时救火。DNS 那一段则提醒我，配置生效这件事，总得去实际运行的那一层确认。

目前服务端的连接、计量、停用恢复以及备份恢复都有验收记录，但没有做长时间的客户端稳定性观察，DNS 调整之后也仍需要在客户端复测。因此，这篇先记录已经查清楚的过程，长期体验留给后续使用慢慢补充。

有一台自己的 VPS，乐趣大概就在这里：把几个原本只在教程里见过的名词接起来，再一点点弄明白，它们究竟是怎么一起工作的。
