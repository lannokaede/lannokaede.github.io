平时拿大模型查 Go 文档、刷题或者随手跑段验证代码，现成的对话壳子用久了总觉得别扭——要么工具权限给得太放飞，要么请求断在半路就得重头再来。干脆自己用 Go 搓了一套个人向的 Agent 宿主，起名叫 [LanAgent](https://github.com/lannokaede/LanAgent)。

现在终端 CLI 和独立的 MCP 服务共用这一套宿主。知识库里灌了 17 份 Go 官方文档，按 512 字符、64 重叠切出 1,206 个片段；写完的练习代码直接扔进本地 Docker 容器里跑测试，不碰宿主机环境，省心。

## 检索和入库拆出去做 MCP 服务

文档检索和入库没塞在主进程里，单拆了个 MCP 服务出来，入口统一卡鉴权和并发数，队列满就直接拒掉。

查资料本身很快，直接同步返回就行；但切分文档、算向量、写库一套走下来太耗时，硬等着极容易超时。所以入库干脆做成异步任务：先丢进去拿个任务编号，后面再按编号查进度。

## 把工具循环和上下文管住

外层 ReAct 循环用 LangGraphGo 串着。放模型自己调工具最怕两件事：跑偏了死循环狂烧额度，或者顺手把我本地文件改坏。宿主这层直接卡死了最大轮次和预算上限，工具走白名单，参数进执行前先过一遍 JSON Schema；文件类工具默认只读，真要写文件必须显式放行。

请求进来先过一层规则路由，能直接答的就不绕工具循环。拿不准的再扔给小分类模型，要求按严格 JSON Schema 给结果；分类接口要是挂了或者吐出脏格式，直接退回默认路径，不拖死主流程。

对话一长就得裁历史消息。之前踩过个很经典的坑：按条数硬截断，一不小心就会把模型刚发的 `tool_call` 和后面对应的工具返回给劈成两半，下一轮接口直接报错。后来改成按完整的“调用 + 返回”消息组来删；做历史摘要要是调失败了，也直接退回整组裁剪。

## 并发队列和流式重试的小细节

SSE 流式和普通非流式请求走同一套模型调用封装，里面卡着在途请求上限和等待队列，满了立刻报错返回。

写退避重试的时候有个坑挺容易顺手写漏：要是攥着并发槽位不放就在那 `sleep` 等重试，来几个慢请求就能把整个池子占死。所以每次准备退避前，先把槽位还回去，下一轮再重新排队。至于 SSE 流式输出，只要第一个数据包发给前端了，后面就不再自动重试，免得两段回复拼成一团乱码；11 月中旬又顺手补了一条防线，非流式接口如果只吐了半截不完整响应也会直接拒掉。

## 中断后怎么续跑，又不乱重放

模型节点和工具节点之间每次流转，宿主都会把 Checkpoint 和执行 ID 落到本地。中途挂掉或者断网，拿原会话 ID 拉起来接着跑就行，已经出结果的节点直接复用旧数据。后面修 bug 时又补了两处落盘细节：替换 Checkpoint 之后显式持久化会话目录，另外一旦 Checkpoint 存储失败就直接停掉后台的 research worker，免得状态越跑越岔。

真正麻烦的是那些可能改了外部状态、但本地还没来得及记下回执的调用。恢复时我会拿参数哈希去工具服务查一遍执行收据：确认跑过就直接沿用结果，查不到收据就把会话停在待核对状态——宁可先卡住让我看一眼，也绝不闷头再重放一遍写操作。

上线前拿本地代理做过一次故障注入测试：让模型刚调完 `read_file`，上游就连续甩回来三次 HTTP 503。重试耗尽后任务停住，拿原会话 ID 恢复跑完，回头翻执行日志，`read_file` 从头到尾只跑了一次。[完整的验收记录](https://github.com/lannokaede/LanAgent/blob/main/docs/harness-validation.md)都放在仓库文档里。

## SQLite 配 Milvus 管本地记忆

个人记忆的正文和版本号存在 SQLite 里，语义检索靠外部的 Milvus，算是个按需开的模块。

改写或删一条记忆时，SQLite 在同一个事务里把新正文、新版本号和待同步记录一块写进去，后台任务再拿着租约去刷 Milvus。向量库同步总归有延迟，失败重推还可能带出旧数据，所以我从来不把向量召回的结果直接塞进上下文，每次都拿着记录 ID 回查一遍 SQLite——版本号对不上的、已经删掉的，全在这一步拦掉。
