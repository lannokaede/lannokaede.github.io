[LanAgent](https://github.com/lannokaede/LanAgent) 是用 Go 写的个人向 Agent 宿主，终端 CLI 和独立的 MCP 服务共用同一套核心调度。知识库导入了 17 份 Go 官方文档，按 512 字符、64 字符重叠切出 1,206 个片段；生成或修改的代码统一放在本地 Docker 容器里跑测试，避免直接影响宿主机环境。

## 把检索和入库拆成 MCP

文档检索和入库没有直接耦合在主进程里，而是拆成独立的 MCP 服务，入口统一做鉴权与并发限制，队列满时直接拒绝请求。

检索本身耗时很短，同步返回即可；入库涉及切分、计算向量和写入存储，同步等待容易超时，所以改成了异步任务，先返回任务 ID，后续按 ID 查询进度。

## 工具循环与上下文裁剪

外层 ReAct 循环基于 LangGraphGo 编排。宿主层对最大轮次和预算上限做了硬限制，工具采用白名单机制，参数在执行前都会先经过 JSON Schema 校验；文件类工具默认只读，写操作需要显式放行。

请求进来先经过规则路由，能直接回答的问题不走工具循环；拿不准的请求再交给小分类模型按严格 JSON Schema 输出路由结果，分类失败或格式异常时退回默认路径。

长对话裁剪历史消息时，按条数硬截断容易把 `tool_call` 和对应的工具返回拆成两半，导致下一轮接口报错。后来改为按完整的“调用 + 返回”消息组来删除；历史摘要调用失败时也同样退回整组裁剪。

## 并发队列与流式重试

SSE 流式和非流式请求共用同一套调用封装，统一限制在途并发数和等待队列长度。

退避重试时有一个细节容易忽略：如果一直占着并发槽位等待重试，几个慢请求就会把池子拖死。每次进入退避前都会先释放槽位，下一轮再重新排队。对于 SSE 流式输出，只要第一个数据包已经发给前端就不再自动重试，避免两段内容拼在一起；非流式接口如果返回不完整响应也会直接拒绝。

## 断点续跑

模型节点和工具节点每次流转都会把 Checkpoint 和执行 ID 落盘，中断后拿原会话 ID 恢复即可复用已完成节点的结果。替换 Checkpoint 后会显式持久化会话目录，一旦 Checkpoint 存储失败就立即停掉后台的 research worker，避免状态继续漂移。

对于可能修改外部状态、但本地还没来得及记下回执的工具调用，恢复时会用参数哈希去工具服务查询执行收据：查到收据直接沿用结果，查不到则把会话停在待核对状态，不会自动重放写操作。

上线前通过本地代理做过故障注入测试：在模型刚调完 `read_file` 后让上游连续返回三次 HTTP 503，重试耗尽后任务暂停，拿原会话 ID 恢复跑完，执行日志里 `read_file` 只运行了一次。完整的验收记录放在仓库的 [harness-validation.md](https://github.com/lannokaede/LanAgent/blob/main/docs/harness-validation.md)。

## SQLite 与 Milvus 记忆同步

个人记忆的正文和版本号存在 SQLite，语义检索走外部 Milvus，作为按需开启的模块。

修改或删除记忆时，SQLite 在同一个事务里写入新正文、新版本号和待同步记录，后台任务持租约刷到 Milvus。由于向量库同步存在延迟，召回结果不会直接放进上下文，每次都会拿记录 ID 回查 SQLite，把版本号不一致或已删除的条目过滤掉。
