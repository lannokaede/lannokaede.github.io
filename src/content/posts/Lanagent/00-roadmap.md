平时拿大模型查 Go 文档、刷面试题或者跑一段验证代码，总觉得套个现成对话壳子不太顺手：要么工具权限太宽，要么请求断在半路就得重头来过。后来干脆用 Go 自己写了一个个人向的 Agent Harness，起名叫 [LanAgent](https://github.com/lannokaede/LanAgent)。

现在终端 CLI 和独立的 MCP 服务共用这一套宿主逻辑。知识库里塞了 17 份 Go 官方文档，按 512 字符、64 重叠切成了 1,206 个片段；写好的练习代码直接丢进本地 Docker 容器里跑测试，不碰宿主机环境。

## 把检索和入库拆成 MCP 服务

文档检索和入库没有写死在主进程里，而是拆成了单独的 MCP 服务，入口统一拦鉴权和并发数，队列挤满了就直接拒掉。

查资料这种很快的操作直接同步返回，但文档切分、算向量、写库太耗时，硬等很容易超时，所以入库做成了异步任务：提交后先拿到一个任务编号，后面再按编号查进度。

## 管住工具循环和上下文长度

外层的 ReAct 循环用 LangGraphGo 编排。让模型自己调工具最怕两件事：一是跑偏了死循环烧额度，二是顺手改坏本地文件。我在宿主这层卡死了最大轮次和预算上限，工具列表走白名单，参数进执行前先过一遍 JSON Schema；文件类工具默认只读，真要写文件得显式放行。

请求进来后先过一遍规则路由，能直接回答的就不进工具循环；拿不准的再交给小分类模型走严格 JSON Schema 判一下，分类接口报错或者输出不合规时，直接退回默认路径，不卡死主流程。

对话变长后需要裁剪历史消息。这里踩过一个常见的坑：如果按条数硬截断，很容易把模型刚发出的 `tool_call` 和后面对应的工具返回拆散，下一轮接口直接报消息格式错。所以我改成按完整的“调用 + 返回”消息组来删；需要做历史摘要时如果调用失败，也直接退回整组裁剪。

## 并发队列和流式重试的细节

流式 SSE 和普通非流式请求共用同一层模型调用封装，里面卡着在途请求上限和等待队列，队列满就立刻报错返回。

做退避重试时有个细节容易忽略：如果在拿着并发槽位的情况下 `sleep` 等重试，几个慢请求就能把整个池子占死。所以每次准备退避前，都会先把并发槽位还回去，等下一轮再重新排队。至于 SSE 流式输出，只要第一个数据包已经发给前端，后面就不再自动重试，免得两段回复拼成一团乱麻。

## 中断后怎么续跑，又怎么防重放

每次在模型节点和工具节点之间流转，宿主都会把 Checkpoint 和执行 ID 落到本地。中途挂掉或者网络断开，重新拉起原会话时，已经拿过结果的节点直接复用旧数据。

麻烦的是那些可能有外部写入、但本地还没来得及记下回执的调用。恢复时我会拿参数哈希去工具服务核对一次执行收据：确认跑过就直接沿用状态，实在查不到收据就把会话停在待核对状态，宁可卡住让人看一眼，也不盲目重放一遍写操作。

上线前拿本地代理做过一次故障注入：让模型在刚调用完 `read_file` 之后，上游连续返回三次 HTTP 503。重试耗尽后任务停下，接着用原会话 ID 恢复跑完，翻前后的执行日志，`read_file` 从头到尾只跑了一次。[完整的验收记录](https://github.com/lannokaede/LanAgent/blob/main/docs/harness-validation.md)放在仓库文档里。

## SQLite 加 Milvus 的本地记忆

个人记忆的正文和版本号存在 SQLite 里，语义检索靠外部的 Milvus，算是个按需开启的模块。

改写或删除一条记忆时，SQLite 会在同一个事务里把新正文、新版本号和一条待同步记录一起写进去，后台任务再拿着租约去更新 Milvus。因为向量库同步总会有延迟，甚至可能因为失败重推引入旧数据，所以每次向量召回回来都不会直接塞进上下文，而是拿着记录 ID 回查一遍 SQLite——版本号对不上的、已经标记删除的，全在这一步滤掉。
