理解本地模型与工具循环之后，再看 A2A，会发现学习重点发生了变化。远程调用方看不到服务内部的 goroutine 和业务对象，它需要一个稳定的任务身份，才能在等待、断线或补充信息以后继续交流。

所以我给 A2A 安排的学习路线，是先把本地任务做好，再学习协议消息。

## 先设计不依赖长连接的流程

最小流程可以是提交目标、返回任务 ID、查询进度和获取结果。然后再加入取消与澄清，明确终态是否还允许变化。

当前 Lanagent 用官方 Go SDK 接入 A2A JSON-RPC，支持发现卡片、异步提交、查询、取消和澄清续接。客户端提交后轮询，底层复用 PostgreSQL 持久任务，没有另造一套内存任务中心。

A2A 允许用有生命周期的任务表达持续工作，也包含需要输入和终态等情况；详细语义可以查[任务生命周期说明](https://a2a-protocol.org/latest/topics/life-of-a-task/)。协议版本可能演进，实际接入需要与 SDK 一起固定。

## 一次澄清，为什么还要保持原任务身份

假设调用方提出召回目标，但缺少预算，需要补充信息。如果每次回复都暴露一个完全独立的新任务，调用方就得自己拼接上下文和进度。

当前实现保留首个运行 ID 作为公开任务 ID，补充输入后创建内部子运行。查询和取消沿数据库父子关系找到当前运行。这个设计把“对外仍是一件事”和“内部新增一次执行”区分开，也避免重启后依赖丢失的内存映射。

消息重试同样需要幂等。同一个消息 ID 应复用相同内容，改内容就应拒绝；补充一条新信息则使用新消息身份。

## 协议状态还需要业务解释

缺少预算与等待人审核，都可能表现为需要输入，但对应的下一步操作不同。当前实现通过业务状态元数据区分，人工审核仍在经营页面完成，不能用一条普通 A2A 回复直接批准发布。

自然语言里说“预算三千元”，也不会自动获得可信预算字段的所有保证。模型理解与服务端校验之间，仍然需要明确的转换和责任。

取消也有边界。它能阻止后续执行，不能撤销已提交草案。调用方需要查询业务结果，才能决定是否另行修改或作废。

## 先把有限能力做完整

当前没有开放流式、推送、列表或历史等能力，发现卡片也不应宣称支持这些功能。进程内的分析/规划分工与 A2A 接入独立存在；当前双 Agent 并没有靠远程协议互相调用。

我后续想围绕重新连接做练习：提交后关闭客户端，再按任务 ID 查询；任务澄清后重启服务，再检查公开 ID 和当前运行；取消与完成同时发生时，核对最终状态。

这让我更愿意把协议学习放到可靠性之后。能够把一次消息发出去只是开始，让另一端持续认出同一件工作，才是远程协作真正需要的基础。
