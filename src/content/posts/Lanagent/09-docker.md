Docker 对我最初的作用是统一环境：数据库和依赖启动起来，本机代码就能运行。到了 Go 练习模块，容器开始承接用户或模型提供的代码，学习重点随之变成了限制执行范围。

这部分属于独立练习 Agent，经营 Agent 和 MCP 都没有代码执行工具。

## 先让执行过程可重复

我整理的第一步是固定镜像、Go 版本、题目、测试和命令。候选代码进入同一个环境，才能比较测试结果，排查编译错误和运行差异。

接下来再学挂载、用户身份、网络和资源。每增加一项限制，都要确认它是否真正作用在容器里，而不只是应用配置中有一个字段。

当前工具只接受候选代码，题目与测试由服务端绑定；执行前检查 AST 契约和导入白名单。模型不能提交任意 shell、测试命令或挂载路径。

## 运行得起来以后，再练习让它停下来

死循环、不断输出和大量创建 goroutine，都是很适合检查边界的练习。执行超时后，还需要停止并清理容器，限制收集的输出，避免“任务已经失败，后台仍在运行”。

当前容器禁网、使用非 root 用户、采用只读根目录和只读工作区，并限制 CPU、内存、PID、执行时间与输出。调用工具本身也有次数和并发预算。

Docker 容器默认不会自动获得资源上限，具体约束需要显式设置，可以查[资源限制文档](https://docs.docker.com/engine/containers/resource_constraints/)。容器共享宿主机内核，隔离能力也需要结合宿主机和 Docker daemon 的权限理解。[Docker 安全文档](https://docs.docker.com/engine/security/)提供了相关背景。

## 测试通过的是哪份代码

这个问题比“测试有没有通过”更细。模型可能先生成候选 A，测试通过，随后在最终答复里把代码修改成 B。如果页面仍然显示已通过，用户就会误以为 B 也经过验证。

当前工具结果携带代码 SHA-256，服务端再比较最终建议代码的哈希。只有同一代码快照确实获得 passed，才生成对应验证信息；该字段不能由模型自己填写。

我觉得这是很值得保留的工程习惯：把证据绑定到明确对象。后续做文件生成、方案审核和部署时，也会遇到“检查的是旧版本，展示的是新版本”的问题。

## 测试结果应该怎么读

固定测试通过，只能说明这份代码通过了这组测试。仍可能有没覆盖的输入，也不能由此推导容器绝对安全。

当前诊断工具有自己的并发限制，原练习运行队列又是另一条入口。统计整个系统可能运行多少容器时，需要把两条入口一起考虑，不能只看其中一个信号量。

Docker 的学习因此从几条启动命令，延伸到一段完整生命周期：准备环境、验证输入、获得执行预算、运行、收集证据、停止和清理。每一步都有边界，才比较容易知道一次测试究竟证明了什么。
