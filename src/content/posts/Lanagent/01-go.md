写 Agent 后端时，Go 最吸引我的地方是启动并发很方便。模型请求、后台任务、状态写入，都可以放进 goroutine。可一旦把“请求开始了”写出来，接下来就得回答：请求什么时候结束？调用方离开之后，后台还应不应该继续？

这些问题让我把 Go 的学习重点，从语法逐渐挪到任务生命周期上。

## 从同步调用开始，再加入并发

我给自己的学习顺序是先写同步版本：一个 HTTP 请求调用业务方法，业务方法调用模型或数据库，每层返回错误。把参数、返回值和错误责任理顺之后，再把耗时操作移到后台。

接口适合围绕实际使用方定义。模型调用、任务存储和业务工具各自需要哪些方法，就从这些需求出发；一开始就搭很大的通用接口，反而容易让调用关系变得难看清。

并发部分先练三件事：等待一组任务、保护共享状态，以及让阻塞中的任务退出。channel、Mutex 和 WaitGroup 都在这里使用，关键是知道哪一处数据由谁拥有。

## context 把取消传下去

Lanagent 的一次经营任务会经过等待模型槽位、发起请求、读取模型流和执行工具。取消必须沿着这条链传递，否则页面显示已取消，底下的模型调用却可能仍在消耗资源。

Go 的 context 用来跨调用边界传递期限和取消信号。它需要下游主动配合：等待 channel 时检查 `Done()`，HTTP 请求带上 context，数据库使用支持 context 的方法。取消信号不会强行杀掉任意 goroutine。[Go 官方的 context 介绍](https://go.dev/blog/context)解释了这套协作方式。

我用来练习的最小例子是：一个生产者持续发任务，一个消费者故意处理得很慢，中途取消。检查时同时看生产者、消费者和等待它们的调用方是否都能返回。只看最外层函数返回，很容易漏掉残留任务。

## worker 数量只是第一道边界

当前经营任务用固定 worker 执行，任务记录保存在 PostgreSQL。内存中的唤醒 channel 只负责提醒，有没有任务仍以数据库为准。

固定 worker 限制同时执行的数量，但排队数量还需要另设上限。否则请求虽然没有同时调用模型，却可能在等待队列里越积越多。学习到这里，我才开始把“并发限制”和“接入容量”分开考虑。

服务退出也有顺序：停止接新任务，通知执行中的任务取消，等待它们结束，再释放连接。任务失败后的状态收尾可能需要短暂独立的期限，因为原任务的 context 此时已经取消；这个收尾期限同样必须有上限。

## 留给自己的练习

我会依次检查排队时取消、执行时取消、工具失败和 worker panic。每次都观察任务最终状态、资源是否释放，以及下一个任务是否还能执行。

这里还有一个容易混淆的地方：取消只能停止后续工作，已经提交的草案不会自动撤回。那是业务事务的责任，需要查询实际结果再决定如何处理。

现在回头看，Go 并发最值得反复练习的是“所有路径都能结束”。启动任务通常只有一行，退出路径却分散在整条调用链里。把它们画清楚之后，很多难以复现的问题才开始有可追踪的形状。
