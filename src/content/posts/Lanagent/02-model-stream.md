接模型接口时，最容易看到的成果是文字一点点出现。等到模型开始调用工具，流式处理就多了一层要求：一段尚未收完的内容，可能是下一次业务操作的参数。

如果在这里把半截数据当成完整结果，后面的校验再认真，也可能建立在错误输入上。

## 我会先读懂非流式响应

学习顺序可以从完整响应开始：消息里哪些字段是文字，哪些是工具调用，结束原因如何表达，错误如何返回。接着用本地假服务固定返回几种响应，让调用方先形成稳定的输入输出约定。

最后再加入流式传输。这样发生问题时，可以区分是消息协议理解错了，还是读取分片时拼接错了。

SSE 的事件边界与网络读取边界是两回事。一次 Read 可能只拿到半行，也可能拿到多个事件；事件里还可能包含多行 `data`。这些基础规则可以对照 [HTML 标准中的事件流解析说明](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)核对。

## 一次读取不等于一次工具调用

工具参数本身也会被拆开。例如一个 JSON 对象，第一段只有字段名，后面才到字符串内容和右括号。同一响应里还可能包含多个工具调用，必须按上游提供的索引归并，保留各自的标识、名称和参数。

我给这部分整理了四层处理顺序：

1. 网络层收字节，并限制总量与等待时间。
2. SSE 层识别完整事件，处理行和事件边界。
3. 模型协议层累计文字、工具增量和用量信息。
4. 结束后检查响应是否完整，再解码、校验工具参数。

当前项目的模型网关会重组工具参数，并检查结束标记和大小限制。这里的接口按所接入的 OpenAI 兼容协议处理；“兼容”也需要逐项验证，不能假定所有供应商返回完全一样的数据。

## 断流以后，留下的内容叫什么

如果已经收到一段自然语言，随后连接中断，可以保留它帮助排查；如果收到的是未闭合的工具 JSON，就不能拿去执行。即使 JSON 恰好闭合，也还要核对协议是否正常结束、调用是否完整。

我想补充的解析练习，是把同一份固定响应按不同位置切开：在字段名中间、转义字符旁边、两个事件之间，以及工具结束之前断开。正确解析器应当对合法分片得到相同结果，对截断输入明确报错。

费用也有类似边界。已经收到的 usage 可以累计；取消或断流后，没有收到最终用量，就应保留“未知”的可能，不能据此声称没有费用。

## 前端流与上游流分开理解

Lanagent 当前经营页面查询的是持久任务状态，并没有直接消费模型 SSE。上游使用流式接口，是模型网关的实现细节；页面是否流式展示，要由产品交互和恢复需求另行决定。

这块学习让我开始重视“完整”这个词。能解析一段 JSON，只代表格式成立；能执行一个工具，还需要完整响应、参数契约、身份范围和业务规则同时成立。
