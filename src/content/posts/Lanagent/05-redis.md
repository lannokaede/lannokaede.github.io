学习 Redis 时，我最先想到的是缓存。可在当前经营链路里，Redis 承担的是请求保护：限制一个身份在一段时间内发起过多写请求。发券名额和预算依然由 PostgreSQL 处理。

从这个较小的用途开始，反而能把原子操作和故障边界看得更清楚。

## 先实现一个进程内窗口

我整理的路线是先不用 Redis，用 map 和 Mutex 写分钟窗口：同一身份有哪些请求已登记、当前计数是否达到上限，以及窗口何时清理。再开两个实例，观察本地计数无法共享的问题。

这时引入 Redis，就有了明确目标：让多个调用方使用共享的判断结果。接下来再比较固定窗口、滑动窗口和令牌桶，会更容易理解各自解决什么。当前项目使用分钟窗口，不能直接把它介绍成令牌桶。

## 为什么把几条命令放进 Lua

检查计数、记录请求、设置过期如果分开执行，并发请求可能在检查和写入之间穿插。项目把窗口时间、请求是否已存在、数量判断和登记放在同一段 Lua 中执行。

Redis 保证脚本执行的原子性；脚本执行期间会阻塞其他服务活动，因此内容需要短小、有界。[Redis 的脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)解释了这两个相伴的特性。

当前实现以身份区分窗口，并记录请求 ID 摘要。同一窗口中重复提交相同 ID，不再新增计数。这只能帮助限流层识别重复登记，实际操作是否成功仍要看业务回执。

## Redis 失效以后，还剩什么

项目先经过本地窗口，再尝试 Redis；Redis 连接故障时退回本地保护。这样单个实例仍有请求上限，但多个实例之间失去了共享计数，整体额度会随实例数量变化。

还有一个细节：本地先登记，随后 Redis 拒绝，这次请求仍可能占用本地窗口。理解这个顺序之后，就不该把计数解释为成功业务次数。限流是在保护资源，允许一定程度保守拒绝；收费或结算则需要更严格的事实记录。

我想用来复习的故障练习包括断开 Redis、让调用超时、跨越分钟边界和重复使用请求 ID。每次观察返回值、本地窗口以及降级状态，而不是只验证正常连接时能不能限住。

## 暂时不给经营数据加缓存

当前经营活动信息没有放进 Redis 缓存。后续如果读压力确实需要缓存，再讨论哪些字段可短暂过期、发布后如何失效，以及是否会误导审核页面。

这一阶段的收获是能明确说出 Redis 对系统增加了什么保证。Lua 把 Redis 内的判断合成原子步骤；跨到 PostgreSQL 的领券事务，仍然需要自己的约束和幂等设计。
