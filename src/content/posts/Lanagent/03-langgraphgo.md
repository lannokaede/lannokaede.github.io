刚接触 Agent 编排时，我容易把注意力放在框架能画出多少节点。后来把商家经营场景拆开，最核心的循环其实很短：模型查看消息，决定调用工具；工具返回结果；模型继续判断，直到给出最终答复。

真正需要花时间的，是每一次状态变化携带什么，以及哪些事情绝不能交给模型自己决定。

## 学图之前，先写出循环

我整理的学习路线从一个普通循环开始：只注册一个查询工具，限制调用轮数，完整保存工具调用与返回，再加入第二个工具。这个阶段要观察模型什么时候停止、工具错误怎样回到上下文，以及非法参数如何处理。

然后再引入状态图。项目使用 `smallnest/langgraphgo`，当前 Runner 里是 model 和 tools 两个节点：模型有最终结果时结束，否则执行工具再回到模型。框架概念和 API 可以查[项目仓库](https://github.com/smallnest/langgraphgo)，具体行为仍应以项目锁定版本为准。

图的好处是让控制流显式可见。消息、待执行工具、累计用量和轮数属于本次运行状态，每次运行各自创建，避免不同任务混用上下文。

## 六个工具背后，仍然是普通业务代码

当前经营 Agent 可以查询销售、预览客群、查看历史、试算活动、保存草案和查询复盘指标。模型不能直接发布、领券或核销。

例如用户希望做一场召回活动，模型可以先查客群，再试算名额和面额，最后保存草案。保存时 Go 业务层重新校验预算和字段，即使模型遗漏独立试算，也不能绕过保存校验。

这让我改变了看待工具描述的方式。Prompt 能帮助模型选对步骤；实际权限来自可用工具集合，预算、归属和版本则来自业务方法。金额使用整数分，计算还要处理边界与溢出。

## 为什么拆成分析和规划

当前版本把只读分析与方案生成分成两个顺序 Runner。分析角色只拿四个查询工具，规划角色再使用包含试算和草案保存的工具集。两者共享任务期限和累计用量，使用同一模型提供者也能工作。

这样的拆分让我能更清楚地观察：哪些内容来自业务查询，哪些属于方案建议。它也增加了一次模型阶段，因此下一步需要比较延迟、费用和草案质量。实现了两个角色，并不能直接推出效果提升。

## 自动重试要先看副作用

纯查询失败通常比较容易重试；保存草案则可能已经提交，只是结果没有返回。当前 Runner 没有配置节点自动重试，事件持久化失败也会停止后续执行。业务层的幂等与版本校验负责帮助调用方核对实际结果。

同样，任务轨迹持久化与图检查点不同。当前能识别任务中断，没有交付从任意图节点精确续跑的能力。要做续跑，还得设计状态快照、工具副作用和重放语义。

我现在理解编排框架的学习目标，是能清楚描述每条边为什么存在、状态由谁更新、失败落在哪里。节点少一些也没关系，只要业务行为能解释、能核对。
