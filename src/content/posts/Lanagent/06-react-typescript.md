写后端时，一个任务可以拥有很多状态。到了页面上，用户首先想知道的往往只有几件事：请求有没有收到，现在在做什么，接下来需要我操作吗？

Lanagent 的经营工作台让我开始从这个角度重新整理 React 和 TypeScript 的学习路线。

## 从静态数据做起

我会先用固定数据搭出经营概览、活动列表和详情，学习组件拆分、列表 key、受控表单和事件处理。这个阶段先把页面上的信息关系理顺：哪些是活动配置，哪些是执行记录，哪些属于指标。

然后再接 API，补加载、空结果、错误和重复点击。TypeScript 类型从接口返回的数据开始写，避免页面各自猜测同一个字段的含义。对可能缺失的数据明确处理，比在多个位置写非空断言更有帮助。

## “已受理”之后还有很多步骤

当前经营请求返回运行记录，页面随后查询持久任务状态。后端受理成功，只能说明任务进入处理流程；草案保存完成，也还需要人工审核才能发布。

我希望页面能够对应这些差别：排队时允许等待或取消，需要补充信息时展示输入入口，草案待审时引导查看具体版本，执行失败时保留可理解的原因。

按钮能不能点击，也应依赖明确状态。浏览器里暂时禁用按钮只能减少误触，最终版本检查仍在服务端。另一个页面修改了活动之后，本页提交旧版本，应当能得到冲突反馈并重新加载。

## 用类型帮助自己发现遗漏

复习时，我喜欢拿一个简化任务模型练习：

```ts
type RunView =
  | { status: "queued" | "running"; id: string }
  | { status: "needs_input"; id: string; question: string }
  | { status: "awaiting_review"; id: string; draftId: string }
  | { status: "failed"; id: string; message: string };
```

这是表达状态的学习示例，并非项目完整 DTO。它的价值在于让“待补充信息必须有问题”“待审核必须找到草案”更容易被检查。服务端响应还需要运行时校验，TypeScript 类型不会验证网络传来的 JSON。

## Effect 留给需要同步的地方

轮询任务是页面与外部系统的同步，需要处理组件卸载、任务切换和旧响应晚到。练习时可以故意让旧请求更慢，观察它是否覆盖了新任务。

而列表过滤、显示文案等能够从现有数据推导出的值，可以在渲染时计算；用户点击发布触发的请求，则放在对应事件处理里。React 官方关于[可能不需要 Effect 的场景](https://react.dev/learn/you-might-not-need-an-effect)帮助我区分这些责任。

我对前端的理解也因此更具体了：页面要帮助人准确判断系统进展。一个清楚的冲突提示、一段可恢复的任务记录，和组件是否整洁一样，都会影响这个工作台能不能用。
