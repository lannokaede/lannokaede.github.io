MCP 最初给我的印象是“让模型接更多工具”。等到真要把经营数据开放出去，就会开始关心另一些问题：调用方能看哪个商家的数据？工具参数里是否可以带身份？声明只读以后，服务端究竟做了什么限制？

因此我给自己的入口定得比较小：先把已有查询能力通过标准协议暴露出来。

## 学习顺序从一次普通函数调用开始

先写一个确定输入、确定输出的查询方法，再为它补参数 Schema 和描述。接着用客户端完成发现工具、调用工具和读取错误，最后才考虑让模型参与选择。

这样能够把“协议是否互通”和“模型有没有选对工具”分开验证。前者出错查传输和消息，后者出错再查工具描述、上下文和模型行为。

MCP 的 tools 机制定义工具发现与调用，工具包含名称和输入 Schema 等信息。学习时可以直接对照[工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)，具体实现再以 SDK 和锁定版本核对。

## 当前只开放四个读工具

Lanagent 使用官方 Go SDK，通过 Stateless Streamable HTTP 提供销售汇总、客群预览、活动历史和活动指标查询。没有开放保存草案、发布、核销、任意 SQL 或代码执行。

这些工具复用现有参数解析和商家范围检查。身份由服务端绑定，调用方不能在工具 JSON 中随意指定租户。保留相同的业务入口，也减少了协议接入后重新写一套校验的机会。

当前内部经营 Agent 仍使用静态工具注册表；这个 MCP 服务是对外查询入口，没有动态导入远程工具。把两条路径分开理解，才能说明自己究竟接通了哪一种能力。

## 描述和权限各做自己的事

只读 annotation 有助于客户端理解工具，但实际只读来自服务端仅注册读方法。参数长度、结果大小和调用并发也需要在服务端处理。

当前 MCP 与 A2A 使用不同凭据，协议默认关闭，只面向本地访问。这一版足以练习工具接入和权限隔离；如果以后面向公网，还要设计用户身份、授权范围和凭据生命周期。

## 我会怎样继续练

先使用官方客户端列工具，再调用一个正常查询；然后测试未知工具、未知字段、超大参数、错误凭据和交叉使用另一协议凭据。最后检查响应里有没有多余的业务内部信息。

工具返回的数据也应作为数据处理。即使查询结果里出现一段像指令的文字，也不能因此改变系统权限或把它提升为系统消息。

这部分让我学会先回答“准备开放哪些能力”。工具数量少，反而更容易检查契约是否清楚。等当前范围可靠以后，再决定是否增加写工具，以及它需要怎样的审核和幂等机制。
